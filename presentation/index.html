Paso 2 · Flujo Agéntico & Grafo de Estados

Arquitectura del Grafo (LangGraph 4-Nodes)

A diferencia de cadenas lineales encadenadas, el agente opera mediante un grafo de estados explícito que evalúa guardrails de entrada, clasifica la intención antes de consumir embeddings y aplica verificación de evidencia a la salida.

01

Guardrails de Entrada (`guardrails_input`)

Filtra ataques de Prompt Injection, intentos de jailbreak y lenguaje inapropiado antes de tocar cualquier modelo o base de datos.

Latencia: ~1ms
Entrada: Mensaje usuario
02

Clasificador de Intención (`classify_intent`)

Etiqueta la consulta como CV_QUESTION, GREETING_OR_META o OUT_OF_BOUNDS. Si es fuera de alcance, frena el flujo inmediatamente.

Latencia: ~350ms
Modelo: Llama-3.1 / Groq
03

Vector Retrieval Tool (`retrieve_context`)

Resuelve anáforas conversacionales ("ese proyecto", "esa empresa") y consulta Qdrant Cloud mediante similitud de cosenos.

Latencia: ~180ms
Vector DB: Qdrant Cloud
04

Grounded Generation & Output Guardrails (`generate_response`)

Genera la respuesta fundamentada estrictamente en los chunks recuperados y valida la ausencia de hechos no evidenciados en el CV.

Latencia: ~800ms
Checkpointer: Supabase

Paso 4 · Justificación de Arquitectura & Q&A del Jurado

Defensa de Decisiones Técnicas

Respuestas preparadas ante posibles preguntas avanzadas de evaluación arquitectónica.

1. ¿Por qué utilizar LangGraph en lugar de una cadena simple de LangChain (`LLMChain`)? ▼
Las cadenas tradicionales de LangChain son lineales y opacas. LangGraph introduce un Grafo de Estados Finitos explícito. Esto permite:
• Bifurcación Condicional: Si los guardrails detectan un ataque o una consulta fuera de alcance (`OUT_OF_BOUNDS`), el grafo detiene la ejecución inmediatamente sin tocar el LLM ni gastar dinero en tokens.
• Persistencia Granular: Permite guardar checkpoints en Supabase tras cada nodo individual, lo que garantiza que si el servidor o la red fallan, la conversación se puede reanudar exactamente en el nodo donde se quedó.
2. ¿Por qué integrar Langfuse Cloud SDK v3 para Observabilidad? ▼
A diferencia de los logs en consola que no permiten correlación, Langfuse SDK v3 proporciona trazabilidad completa tipo OpenTelemetry. Permite auditar el payload exacto enviado al LLM, inspeccionar la distancia de similitud de los vectores recuperados de Qdrant, analizar latencias desglosadas por nodo y medir la variación de respuestas entre versiones de modelos.
3. ¿Por qué utilizar Qdrant Cloud en lugar de `pgvector` dentro de PostgreSQL? ▼
Aislamiento de Cargas y Especialización: Separar la base de datos relacional (Supabase para checkpoints) de la base de datos vectorial (Qdrant para embeddings) evita la saturación de conexiones en PostgreSQL durante ráfagas de búsqueda. Qdrant está optimizado en Rust para búsquedas vectoriales HNSW sub-milisegundo con filtros dinámicos por payload (`cv_version`, `tipo`).
4. ¿Por qué se eligió Supabase Session Pooler en lugar de conexión directa? ▼
Los servidores en la nube como Render o soluciones serverless suelen carecer de direcciones IPv6 nativas en planes gratuitos. El Session Pooler de Supabase (puerto 5432) actúa como un proxy PgBouncer en IPv4 que administra eficientemente el pool de conexiones de Python (`psycopg_pool`) manteniendo compatibilidad total con Prepared Statements y autocommit=True.
5. ¿Cómo se garantiza el cumplimiento del estándar Open Responses API? ▼
El backend de FastAPI expone los endpoints /v1/responses y /responses devolviendo estructuras estrictas compatibles con la especificación de Open Responses y el SDK oficial de OpenAI (openai.chat.completions.create). Además, expone /.well-known/agent-card.json para autodescubrimiento e integración automática en catálogos A2A como Parley.
